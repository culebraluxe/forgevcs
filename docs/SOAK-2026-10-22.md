# ForgeVCS P0-4 — 10-agent soak (2026-10-22)

**Owner:** Lane V (fvcs-human-qa)
**Status:** **PASS** for the 10-agent soak on a **process-per-repository** topology.
**Defect found during the run (P0, reported here; FIXED by Lane X, 2026-10-22):** in a *single*
process that has already booted a repository, `POST /repos/{repo}/init` for another repository
returned **503 `unavailable`: `building the engine: UNAVAILABLE: storage metrics: Duplicate
metrics collector registration attempted`**. The soak therefore ran the largest safe topology on
the `ba3fe9a` tree: one single-engine service process per independent repo (10), plus a second
process for one repo to exercise cross-instance behaviour. The defect and the post-fix evidence
are recorded in §7; multi-repo-per-process is supported again (see §6 item 1 and §7).

Environment: local macOS host, **PostgreSQL 16** (`forgevcs_soak`) + **moto S3 over TLS**
(`forgevcs-soak`), service built from `ba3fe9a` ("P0 metrics + P1 merge-engine/topology
hardening"), debug profile. **No production/Neon, no deploy, no VCS commit, no code changes.**
All evidence: `/tmp/forgevcs-soak-2026-10-22/`.

## 2. Workload

- **Setup:** 10 idempotent `init` calls; cross-repo isolation probe per agent (own 200 / foreign
  403); 11 workspaces create→write(`lane/<agent>/ws-note.txt`)→status→destroy (root-write destroy
  is human-DevOps by policy) and 1 workspace `submit` landed; one **workspace-lease conflict**
  (agent holds the lease, human writes through the *other* instance → typed 409, then TTL
  takeover/destroy).
- **Rename path:** `lane/agent-01/old-name.txt` deleted + `new-name.txt` added in one changeset,
  landed; final tree has the new path and not the old (`old_status=404`, `new_status=200`).
- **Cross-instance:** token minted by instance A accepted by instance B (200); two divergent
  changesets landed **concurrently through two processes** into the same repo — both 200,
  `main` v1→v3, both acknowledged targets present in history (shared DB ref CAS worked).
- **Deliberate conflict:** `agent-02` lands an edit, then a divergent head is `merge-land`ed →
  409 with persisted paused conflict (`operation:"merge-land"`, `resolve_parent == ref_target`);
  list → show → resolve → continue → `continued`, main v3→v4, resolved bytes verified.
- **Sequential:** all 10 agents, 3 iterations each (push+land; merge-land on even; lane-ref
  stale-version retry on k=3; refs/log reads).
- **Concurrent:** 10 workers (one per agent, iterations sequential **per agent**, concurrent
  **across agents**), 6 iterations each: push+land, merge-land on even, lane-ref stale-version
  409 retry on multiples of 3, refs/log reads.
- **Retries:** client retries on 409 stale version (re-read ref + CAS version) and on HTTP 5xx
  (bounded 3 attempts, exponential backoff). A synthetic 503→200 endpoint validates the 5xx retry
  path because the harness has no proxy/chaos tool to inject 503 into the service.

## 6. Residual risks / limitations

1. **Single-process multi-repo was broken on `ba3fe9a`** (§7) — the soak topology was
   process-per-repo. **Fixed by Lane X (2026-10-22):** a process can boot multiple repositories
   again; the storage snapshot collectors are registered once per process and aggregate all live
   engines (§7 "After the fix"). Process-per-repo remains a valid topology; the 10-agent workload
   itself was not re-run in a single process, so this is a boot/observability fix, not new soak
   evidence.
2. One host, loopback network; 10 agents are HTTP clients driven by one Python process, not 10
   independent machines/LLM agents. Process kill/restart and network partitions are not exercised.
3. moto S3 is not Neon object storage; PostgreSQL is local 16, not Neon. TLS/S3 semantics are
   representative but not identical.
4. Only 2 instances were run for one repo (port 4154); cross-instance coverage is token
   interchange, concurrent ref CAS and workspace lease — not multi-region/multi-writer fleets.
5. 503 retry behaviour is validated **synthetically** (local 503→200 endpoint); no live 503s were
   observed. No rate-limit/429 path was exercised.
6. Lane-ref retries were seeded deliberately with a stale `expected_version` (30 × 409); this is
   client-visible retry behaviour, not a server failure.
7. Single run, warm caches, debug build; percentiles are per-operation wall time, not steady-state
   throughput or production SLOs. Latency includes the Python client and loopback overhead.
8. A 5 s workspace-lease TTL was set for the harness (`FORGEVCS_WORKSPACE_LEASE_TTL_SECS=5`) so
   cleanup/takeover completes quickly; production default is 300 s.

## 7. DEFECT FOUND — P0: second engine boot in one process fails (503)

**Reproduction:** a process that has booted its startup repo, then receives
`POST /repos/<other>/init` (the documented create/boot route), answers:

```
HTTP/1.1 503
{"code":"unavailable","message":"building the engine: UNAVAILABLE: storage metrics: Duplicate metrics collector registration attempted",...}
```

Retrying does not help (`init-defect-1.json`, `init-defect-2.json`). This blocks any
multi-repo-per-process topology, including a 10-repo soak in one process and the `init` half of
the workspace/R5-style flow for a second repo.

**Root cause (read-only code review):** the P0-metrics work injects one process-wide
`Arc<Metrics>` into every engine (`crates/forgevcs-service/src/engine.rs:111`
`Engine::connect(config, repo, metrics)`; `engine.rs:400` `get_or_boot` clones
`self.metrics`; `main.rs:32` creates the single registry). Each `ServerApp::build` registers the
storage snapshot collectors `scion_storage_access` and `scion_storage_bytes` into that shared
registry (`upstream/crates/scion-server/src/app.rs:251-283`). The second engine's registration is
a duplicate Prometheus collector in the same registry → the `storage metrics: …` UNAVAILABLE
error surfaces through `POST /init`. The commit's own "two engines share one registry" test uses
`Engines::boot` without a real DB/bucket, so it does not exercise a second real engine.

**Suggested fix direction (implemented by Lane X, see below):** register the storage snapshot
collectors once per process (e.g. in `Metrics::new()`/`main`) or name them per repo, and add a
live regression test that boots two real engines (DB+S3) in one process and asserts `/metrics`
serves both.

### After the fix — Lane X (2026-10-22)

**Fix:** `crates/forgevcs-service/src/metrics.rs` now exposes `MetricsHub`:

- the rendered registry is created once per process and the hub registers the two storage
  snapshot collectors into it **exactly once**, summing `scion_store::Counters` over every live
  engine (`scion_storage_access`/`scion_storage_bytes` keep the upstream names, help and labels);
- each engine receives `MetricsHub::engine_view()`: a `Metrics` whose built-in series handles are
  clones of the shared ones (so RPC/land/CAS recordings still reach `/metrics`) but whose
  `registry` is a private scratch registry, so upstream's **per-build** snapshot registration can
  never collide across engines (the scratch registry is not rendered; the aggregate is);
- `Engines` carries the hub, attaches an engine's counters on boot, and detaches them on
  repository delete (`Engines::remove`).

The live before/after reproduction used the same local harness (PostgreSQL 16, moto S3 over TLS
via the harness proxy, one service process, human DevOps token), on two fresh databases:

| Tree | Boot `forgevcs` then `POST /repos/<new>/init` | `/metrics` storage families |
| --- | --- | --- |
| `ba3fe9a` (soak build) | **503** `building the engine: UNAVAILABLE: storage metrics: Duplicate metrics collector registration attempted` | 1 set |
| Lane X worktree (`MetricsHub`) | `repo-after-a` **200**, `repo-after-b` **200** | **1** aggregated set (`scion_storage_access{kind="metadata_calls"} 38` et al.) |

Evidence: `/tmp/fvcs-x2-evidence/{before-init.json,service-before.log,after-init-repo-a.json,
after-init-repo-b.json,metrics-after.txt,service-after.log}` (Lane X, local harness only).

Regression test added in-repo: `crates/forgevcs-service/tests/two_engine_boot.rs`
(`two_real_engines_boot_in_one_process_and_share_metrics`) — boots two real engines against a
real PostgreSQL + S3-compatible endpoint in one process, asserts both boot, exactly one
`scion_storage_access`/`scion_storage_bytes` family with non-zero aggregated boot traffic, land
counters from both engines visible, and detach drops an engine. It is opt-in
(`FORGEVCS_TEST_DATABASE_URL` + `FORGEVCS_TEST_S3_ENDPOINT/BUCKET` + `SSL_CERT_FILE`); a normal
`cargo test` skips it with a message. Hermetic guards in `metrics.rs` also reproduce the old
collision deterministically (second registration on the rendered registry is an error) and prove
engine views cannot collide.

**Topology consequence:** multi-repo-per-process is supported again, so the soak can also be run
as one process with 10 repos. The 10-agent workload itself was **not** re-run in that topology;
the evidence here is the boot/observability fix plus the two-engine live test. Per-repo storage
use is still not broken out as a label (one process-wide aggregate; see
`docs/OBSERVABILITY.md` §2).
